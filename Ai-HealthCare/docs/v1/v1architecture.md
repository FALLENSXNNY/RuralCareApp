# RuralCare — System Architecture

## 0. OFFICIAL STACK DECISION (2026-08-28) — SUPERSEDES DEFERRED-STACK LANGUAGE BELOW

> **This section is the authoritative, current architecture decision.**
> Where older sections below describe the backend/database/auth as "deferred" or
> "not yet decided", THIS section overrides them.

### 0.1 Official Technology Stack

| Layer | Technology | Notes |
|---|---|---|
| **Frontend** | Flutter + Riverpod + GoRouter | Patient app (patient-only scope) |
| **Authentication** | Firebase Authentication | Phone number auth, real SMS OTP, Firebase ID tokens |
| **Backend** | Node.js + Express | REST API, HTTPS |
| **Database** | MongoDB Atlas | Application/patient data |
| **AI** | Gemini API | Accessed ONLY from the backend — never from Flutter |
| **Configuration** | Environment variables | Backend secrets in `.env`; `.env.example` documents required vars |

### 0.2 Responsibility Separation (CRITICAL)

| Concern | Authority |
|---|---|
| **Identity / Authentication** | **Firebase** — verifies phone + OTP, issues ID tokens |
| **Authorization + application logic** | **Node.js backend** — verifies Firebase ID tokens, enforces access rules |
| **Application / patient data** | **MongoDB** — patient records, later: health records |

- SharedPreferences/local storage is **client-side state caching only**.
  It is **NOT** the source of truth for authentication.
- The backend must **never** trust `patientId`, `userId`, `phone`, or `email`
  supplied in request bodies. Identity is **always** derived from the verified
  Firebase ID token.

### 0.3 Authentication Flow (Authoritative)

```text
Patient
   ↓
Flutter (existing OTP UI)
   ↓
Firebase Phone Authentication (real SMS OTP)
   ↓
Firebase verifies OTP → Firebase user (UID) + ID token
   ↓
Flutter sends ID token to backend (Authorization: Bearer <id-token>)
   ↓
Backend verifies Firebase ID token (Firebase Admin SDK)
   ↓
Backend obtains authenticated Firebase UID from the verified token
   ↓
Backend finds or creates patient record in MongoDB (keyed by UID)
   ↓
Returns authenticated patient information
```

Rules:
- No demo/hardcoded OTP. OTP must be a real Firebase SMS OTP.
- Duplicate prevention: patient lookup is keyed by Firebase UID; re-login
  must return the same patient record.
- Flutter route guards are UX only. The backend independently verifies
  authentication on every protected request.

### 0.4 AI Flow (Authoritative — implementation deferred to Phase 7)

```text
Flutter → Node.js Backend → Gemini API → Node.js Backend → Flutter
```

Never: `Flutter → Gemini API` directly. Gemini API keys exist only in the
backend environment.

### 0.5 Secrets Policy

- Backend secrets live in `backend/.env` (git-ignored):
  `MONGODB_URI`, `GEMINI_API_KEY`, `FIREBASE_PROJECT_ID`,
  `GOOGLE_APPLICATION_CREDENTIALS` (path to service-account JSON stored
  OUTSIDE the repo) — see `backend/.env.example`.
- Firebase Admin credentials are NEVER placed in Flutter.
- Gemini API keys are NEVER placed in Flutter.
- MongoDB credentials are NEVER placed in Flutter.
- Flutter receives Firebase config via standard `firebase_options.dart`
  (generated by FlutterFire CLI) — these are public client identifiers,
  not secrets.

### 0.6 Backend Structure (Phase 2 — minimal, do not over-engineer)

```text
backend/
  src/
    config/        # env loading, Firebase Admin init, MongoDB connection
    middleware/    # authenticate (Firebase ID token verification)
    routes/        # auth routes only for Phase 2
    controllers/   # auth controller
    services/      # patient service (find-or-create by UID)
    models/        # User/Patient model (minimal for Phase 2)
    utils/         # error helpers
    app.js
    server.js
  .env             # git-ignored — real secrets
  .env.example     # committed — documents required variables
```

Phase 2 implements ONLY what authentication requires. No doctor/admin/HW
APIs. No medical-record collections beyond minimal patient identity.

### 0.7 Mock Policy (from this point forward)

- New features requiring backend/database/API use **real integrations**.
- No fake success responses, no fake endpoints, no local-state-only
  "functional" buttons.
- Existing mock data may remain temporarily for screens whose
  implementation phase has not started (tracked in `docs/progress.md`).

## 1. Purpose

This document defines the technical architecture of RuralCare.

The architecture must support:

* Flutter mobile application
* Backend API
* Persistent patient records
* Role-based access control
* AI services
* Medical document storage
* Emergency functionality
* Offline functionality
* Synchronization
* Teleconsultation
* Healthcare facility discovery
* Referral tracking
* Diagnostic management

The architecture must remain simple enough to develop and maintain within the MVP timeline.

---

# 2. Architecture Principles

The system follows these principles:

### 2.1 Mobile-first

The primary patient experience is a Flutter mobile application.

### 2.2 Backend as the security boundary

The Flutter application must never be trusted to enforce authorization by itself.

All protected operations must be validated by the backend.

### 2.3 API-first communication

Flutter communicates with the backend through well-defined APIs.

### 2.4 AI as an assistive layer

AI services assist users and healthcare professionals but do not replace clinical decision-making.

### 2.5 Offline-first for critical functionality

Critical emergency information must remain available without internet connectivity.

### 2.6 Modular architecture

Features should be separated into logical modules so they can be developed and tested independently.

### 2.7 Minimal infrastructure

The MVP should avoid unnecessary infrastructure and services.

# 4.1 Design-to-Implementation Workflow

RuralCare follows a **design-first UI development workflow**.

The visual design of the application must be created in **Stitch before the corresponding Flutter implementation begins**.

The workflow is:

```text
Product Requirements
        ↓
Feature Specification
        ↓
Stitch UI/UX Design
        ↓
Design Review
        ↓
Design Approval
        ↓
Flutter Implementation
        ↓
Visual Comparison
        ↓
Refinement
```

## Stitch as Design Source of Truth

For every approved screen, Stitch is the visual source of truth.

The Flutter implementation should reproduce the approved Stitch design as accurately as reasonably possible.

This includes:

* Layout
* Component hierarchy
* Spacing
* Typography
* Colors
* Icons
* Buttons
* Cards
* Forms
* Navigation
* Visual hierarchy
* Interaction patterns
* Loading states
* Empty states
* Error states
* Accessibility-oriented visual elements

Flutter developers or coding agents must not independently redesign an approved screen unless a design change is explicitly requested or approved.

## Design Approval Gate

A feature should have the following states:

```text
REQUIREMENTS
     ↓
DESIGNING
     ↓
DESIGN_REVIEW
     ↓
DESIGN_APPROVED
     ↓
IMPLEMENTATION
     ↓
VERIFICATION
     ↓
COMPLETED
```

Flutter implementation should not begin for a feature whose Stitch design has not reached `DESIGN_APPROVED`.

## Visual Verification

After implementation, the Flutter screen should be compared against the approved Stitch design.

The comparison should verify:

* Overall layout
* Positioning
* Dimensions
* Spacing
* Typography
* Colors
* Icons
* Component appearance
* Navigation
* Interactive states

If significant differences are found, the Flutter implementation should be corrected rather than automatically changing the approved design.

## Design Changes

If the product requirements change after a design has been approved:

```text
Requirement Change
       ↓
Update Specification
       ↓
Update Stitch Design
       ↓
Review & Approval
       ↓
Update Flutter Implementation
```

The coding agent must not silently change both the design and implementation without following this process.

## MCP Usage

The project may use the connected Stitch and Flutter MCP capabilities to support the workflow.

Stitch should be used for:

* Generating UI designs
* Iterating on designs
* Refining visual components
* Producing consistent screens

Flutter tooling/MCP should be used for:

* Implementing approved designs
* Running the application
* Inspecting rendered screens
* Verifying interactions
* Identifying visual discrepancies
* Iterating on implementation

The MCP tools are implementation mechanisms; the approved design and project specifications remain the authoritative references.

# 8. Authentication

All protected application functionality requires authentication.

Authentication must establish:

* User identity
* User role
* Session/token
* Appropriate permissions

The backend must not trust a role value supplied directly by the client without validating it against the authenticated user's server-side identity.

---

# 9. Role-Based Authorization

Authorization should follow:

```text id="b4n1j7"
Authenticated User
       ↓
Determine role
       ↓
Check required permission
       ↓
Check resource access
       ↓
Allow / Reject
```

Example:

```text id="x8shk6"
GET /patients/:id

        ↓

Is user authenticated?
        ↓
Does user have patient-record permission?
        ↓
Is this patient within the user's authorized scope?
        ↓
Return permitted information
```

# 10. Database — MongoDB

MongoDB will be used as the primary persistent database.

The database should store structured application information such as:

* Users
* Patient profiles
* Doctor profiles
* Healthcare workers
* Consultations
* Prescriptions
* Diagnostics
* Referrals
* Appointments
* Follow-ups
* Facilities
* Emergency events
* AI conversation metadata
* Document metadata

Large medical files should not necessarily be stored directly inside MongoDB.

---

# 11. Redis

Redis may be used for short-lived or high-speed data.

Potential uses:

* Appointment queues
* Temporary session state
* Caching facility information
* Rate limiting
* Temporary AI conversation state
* Short-lived synchronization information

Redis should not be treated as the permanent source of truth for medical records.

Permanent healthcare information belongs in persistent storage.

---

# 12. Medical Document Storage

Medical documents can include:

* Prescriptions
* Blood reports
* Diagnostic reports
* X-rays
* ECGs
* Discharge summaries

The architecture should separate:

### File storage

Stores the actual file.

### Database

Stores metadata such as:

* Patient ID
* Document type
* Upload date
* Consultation ID
* Diagnostic ID
* Storage reference
* Uploaded by
* Access metadata

The system must protect document access through authenticated backend authorization.

---

# 13. AI Architecture

AI should not directly access the database.

Instead:

```text id="z25yxd"
User / Doctor
      ↓
Backend
      ↓
Authorization
      ↓
AI Orchestration Layer
      ↓
Select permitted data
      ↓
AI Service
      ↓
Validate / structure response
      ↓
Backend
      ↓
User / Doctor
```

This prevents the AI layer from becoming an uncontrolled database access mechanism.

# 27. Error Handling

The system should distinguish:

### User errors

Example:

> Please select a healthcare facility.

### Network errors

Example:

> You're offline. Your emergency information is still available.

### Server errors

Example:

> We couldn't complete this request. Please try again.

### AI errors

Example:

> The AI assistant is temporarily unavailable. You can still access emergency information and healthcare services.

The application must not expose raw backend stack traces or sensitive implementation details.

# 29. Security Architecture

The system must implement:

* HTTPS
* Authentication
* Role-based authorization
* Resource-level authorization
* Secure document access
* Input validation
* Rate limiting where appropriate
* Secure session management
* Audit logging for important clinical actions
* Minimal data exposure to AI services

The frontend must never contain secrets such as:

* Database credentials
* AI provider secret keys
* Backend administrative credentials

# 30. AI API Key Security

AI provider credentials must exist only on the backend or secure server-side environment.

Never place secret AI API keys directly in Flutter source code.

Correct:

```text id="q5h2x9"
Flutter
   ↓
Backend
   ↓
AI Provider
```

Incorrect:

```text id="y1n8r3"
Flutter
   ↓
AI Provider
```

with a secret key embedded in the application.

Conceptually:

# 37. Architecture Constraints

The implementation must NOT:

* Put medical records directly in Flutter local state only
* Put AI provider secrets in Flutter
* Allow frontend-only authorization
